# FINAL HACKATHON DIRECTION — Evidence-gated delivery, NOT generic inventory integrity

1. **Challenge requirement.** Deliver authentication, KPIs, products, stock by location, categories, reorder rules, receipts, delivery orders, adjustments, movement history, locations/warehouses, low-stock alerts, multiwarehouse and SKU search; log every RECEIVE/DELIVER/TRANSFER/ADJUST. These are mandatory substrate, not innovation. Source: user's brief; no external challenge PDF available.
2. **Existing Veyra substrate.** User describes a digital inventory → blind count → discrepancy → trace → resolve → audit demo. However this working directory was empty before research; no code, documentation, architecture, deployed instance or stack was inspectable. Preserve any actual working implementation when supplied. Do not represent unverified components as shipped.
3. **Commoditized.** Physical counts, variance detection, count work scheduling, review, reconciliation, audit and physical-vs-WMS operational intelligence [S1–S6 in `01_COMPETITIVE_LANDSCAPE.md`]. Hardware CV/RFID is not necessary today.
4. **Killed.** “Integrity + reconciliation + root-cause trace is our unique core”; all standalone scoring, debt, generic next-best count, dashboards and automatic causal explanations. See `02_CURRENT_VEYRA_KILL.md` for A–O.
5. **Unresolved user problem.** Before a real pick, an operator must decide whether *apparently sufficient* digital stock is supported by current physical evidence, especially if a movement happened mid-verification. Human review of unrelated history is slow and an unverified pick may fail. This is a potential workflow gap, NOT a proven industry-wide absence.
6. **New core mechanism.** A **version-bound evidence gate at delivery commit**: block guarded orders when the source-bin/SKU count is missing, stale, disputed or mismatched; identify the one targeted recount; release only on fresh, agreeing evidence; preserve both decisions and all movements. It never automatically declares a cause or adjusts stock.
7. **Competitor defense.** Odoo and Dynamics handle counts and exceptions [S1–S3]; Dexory and Gather AI market reconciliation and ranked actions [S5,S6]. We did not verify from the readable sources an identical *commit-time version-bound* gate, but such rules may exist in commercial WMS/custom ERP. The differentiation is the 2-minute observable combined action in this hackathon, **not exclusivity**.
8. **Exact implementation.** Within the actual stack once located: immutable movement ledger with per-bin/SKU monotonically increasing version; immutable count evidence carrying version *from count start* and witness; policy-tagged high-value orders; one delivery transaction locking bin/SKU rows, comparing balance, evidence, disagreement and relevant events, then writing decision + single delivery movement atomically. Expose `BLOCK(reason, movement IDs, recount task)` or `ALLOW`. Recheck on actual commit, never trust preflight. Multi-line and tenant-aware locking/permissions required. The repo currently contains only `research_probe.py`, not this integration.
9. **Exact demo.** Start bin A/S count 10 at v0 and order 9. Receive 2 → ledger 12 at v1. Try delivery 9: **blocked despite enough recorded stock**; old count was at v0. Recount 12 at v1; retry; exactly one delivery 9, ending balance 3, with persisted before/after evidence. Synthetic seed explicitly disclosed.
10. **Exact data required.** Order ID, SKU, bin/warehouse, quantity and value policy; recorded balance and version; movement ID/type/quantity/source/destination/ref/version; count ID/physical quantity/capture version/start/submit timestamps/counter; policy version and decision actor. Missing or contradictory guarded evidence → hold, not imaginary certainty.
11. **Exact failure cases.** Count missed a movement; two counters disagree; duplicate adjustment/delivery ref; stock moved between preflight and commit; counts recorded late; false positive after legitimate receipt; count itself wrong; no evidence; insufficient quantity; cross-bin transfer; incorrect actor/tenant; two competing orders. In-memory A–K tests cover many *sequential* cases, but not DB concurrency, auth, multi-line orders or real physical truth.
12. **Do NOT build.** LLM chat/report, confidence percentages, generic forecasts, automatic root-cause blame, CV/RFID, ERP replacement, digital-twin graphics, more dashboards, cross-system integrations, new infrastructure.
13. **5–6h execution.** 0–0.5h mount existing repo/verify mandatory substrate; 0.5–1.25h event versions; 1.25–2.25h counts/decision evidence; 2.25–3.25h atomic delivery gate; 3.25–4h thin UI; 4–5h DB/API/race/idempotency tests; 5–6h seed/rehearse/fix challenge gaps. If existing implementation is not provided, **compliance first** and reassess whether gate is achievable; greenfield full substrate + gate is not honestly guaranteed. Details `07_BUILD_PLAN.md`.
14. **30-second pitch.** “A WMS knows it has 12, but does it have evidence that 12 are really in the pick bin? After a receipt invalidates the last count, Veyra stops a high-value delivery even though the ledger says there is enough stock. It tells a worker the single bin to check; a fresh count releases the order and both decisions are traceable. We do not claim counting or reconciliation is new—we make stale evidence change the *actual* fulfillment decision.” Conditional: remove “stops” until server hook exists.
15. **2-minute demo script.** 0–15s show 10 counted/order 9; 15–35s receive 2; 35–75s attempt pick and show *server-side* stale hold despite ledger 12; 75–100s recount 12, retry and deliver once; 100–120s show held→released, v0→v1, movement and audit. Full script `08_DEMO_SCRIPT.md`.
16. **Honest novelty statement.** Broad integrity thesis **killed**. Exact integrated workflow is a **potential differentiation for this demo**, not a proven first-of-kind product. No accessible source settled whether existing ERPs can enforce a comparable rule. Vendor pages partly inaccessible. 11/11 synthetic in-memory cases pass fixed expectations; product not shipped or validated with real workers.
17. **One post-hackathon extension.** With customer consent, add a measured intervention experiment: compare short-pick rate and recount burden for guarded vs existing workflows before tuning policy; avoid uncalibrated risk scores.

**Decision:** Build the gate ONLY on top of a verified working mandatory system, not instead of it. The judge's moment is **“there is enough stock, yet the system refuses this pick because the supporting physical count is stale—and tells me exactly how to release it.”**
