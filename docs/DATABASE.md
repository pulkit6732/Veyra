# Database

SQLite schema in `veyra.py:SCHEMA`, created via `init()` on startup. `init()` sets persistent WAL mode before migrations and creates scope/version indexes for evidence and movements. Each new connection enables foreign keys and a 15-second busy timeout; HTTP GETs use a deferred read snapshot, while mutations use `BEGIN IMMEDIATE`. WAL allows readers and a single writer to overlap, not concurrent writers; long-lived readers can delay checkpoints. Initialization requires WAL support and will fail rather than silently switch to rollback-journal mode. Keep the database and its `-wal`/`-shm` files together for live backups (use SQLite's backup API instead of copying only the main file). Tables: `resolutions` (one explicit adjustment per evidence, note, actor, timestamp, movement reference); `users`, expiring `sessions`; `categories`, `products`, `warehouses`, `locations`; `stock` keyed by `(product_id,location_id)` with integer qty and version; `movements` with unique reference and source/destination, resulting versions, actor and timestamp; `count_sessions` with version/qty captured at start and state; `evidence` linked to one session with observed quantity, version, actor, status and submission time; `deliveries` with unique reference, optional destination, timestamps and persisted state (legacy first-line location/quantities retained); `delivery_lines` with unique (ref, product_id, location_id), per-line requested/picked/packed quantities; `delivery_events` with actor, scope, from/to state, action, increment, inventory version and evidence ID for final commit; `decisions` with stage, reason, relevant evidence ID, stock and version snapshots, actor and timestamp. All quantities are integer units (no fractional UOM conversion). A receive or adjustment bumps its one stock row; transfer bumps each affected row; delivery bumps every source row only when ALL lines pass commit validation. Each delivery movement links `delivery_ref` and `line_id`; first-line movement uses the document ref, later movements use `ref#line_id`. Decisions and delivery events have a nullable line_id for historical records and per-line new records. Investigation derives expected quantity from the linked count session and compares its captured version to current stock; it selects relevant movements touching that SKU/location with versions after the previous verified count (or the selected count) up to the current version, returning at most 50 with an exact event total. A resolution is inserted atomically with its adjustment movement under `BEGIN IMMEDIATE`, only for the latest still-current discrepant evidence; the version bump makes that evidence stale and forces a recount. `opening_balances` contains one `OPENING_BALANCE` checkpoint per stock scope: imported recorded qty/version, capture timestamp, and `after_movement_id` (highest movement ID already present at capture). It is not a physical count, receipt, or claim about the date/origin of the stock. Startup backfills existing stock at its then-current qty/version; an AFTER INSERT stock trigger captures new rows (including seed and zero scopes) in the same transaction. Seed sets S = 768 and B = 5 at WH/A, both version 0, with two opening checkpoints; reruns skip existing products and do not change checkpoints. To replay a bin, start at its checkpoint and apply scoped movements with ID greater than `after_movement_id` in ID order, verifying each resulting bin version increments by one. Earlier movements on migrated databases remain historical records, but cannot always be replayed back to their original balance. No stock quantity or version is modified by backfill. Schema, delivery migrations, checkpoint backfill and trigger creation commit together or roll back together (WAL mode is configured separately). References are globally unique across movements and delivery orders, and a new DONE order shares its reference with its first-line delivery movement. Startup migrates legacy PENDING/CANCELED deliveries to DRAFT, retains DONE and all linked decisions, without inventing prior pick/pack events. P2 migrates existing P1 orders to one line using additive schema changes, preserving decisions and movements; repeated starts do not duplicate lines or checkpoints. Back up the DB before migration; new installs initialize the latest schema.
