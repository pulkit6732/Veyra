# Database

SQLite schema in `veyra.py:SCHEMA`, created via `init()` on startup. Tables: `resolutions` (one explicit adjustment per evidence, note, actor, timestamp, movement reference); `users`, expiring `sessions`; `categories`, `products`, `warehouses`, `locations`; `stock` keyed by `(product_id,location_id)` with integer qty and version; `movements` with unique reference and source/destination, resulting versions, actor and timestamp; `count_sessions` with version/qty captured at start and state; `evidence` linked to one session with observed quantity, version, actor, status and submission time; `deliveries` with unique reference, optional destination, timestamps and persisted state (legacy first-line location/quantities retained); `delivery_lines` with unique (ref, product_id, location_id), per-line requested/picked/packed quantities; `delivery_events` with actor, scope, from/to state, action, increment, inventory version and evidence ID for final commit; `decisions` with stage, reason, relevant evidence ID, stock and version snapshots, actor and timestamp. All quantities are integer units (no fractional UOM conversion). A receive or adjustment bumps its one stock row; transfer bumps each affected row; delivery bumps every source row only when ALL lines pass commit validation. Each delivery movement links `delivery_ref` and `line_id`; first-line movement uses the document ref, later movements use `ref#line_id`. Decisions and delivery events have a nullable line_id for historical records and per-line new records. Investigation derives expected quantity from the linked count session and compares its captured version to current stock; it selects relevant movements touching that SKU/location with versions after the previous verified count (or the selected count) up to the current version, returning at most 50 with an exact event total. A resolution is inserted atomically with its adjustment movement under `BEGIN IMMEDIATE`, only for the latest still-current discrepant evidence; the version bump makes that evidence stale and forces a recount. Initial seed sets S = 768 and B = 5 at WH/A, both version 0, without creating synthetic receipts and is for a new demo database only. References are globally unique across movements and delivery orders, and a new DONE order shares its reference with its first-line delivery movement. Startup migrates legacy PENDING/CANCELED deliveries to DRAFT, retains DONE and all linked decisions, without inventing prior pick/pack events. P2 migrates existing P1 orders to one line using additive schema changes, preserving decisions and movements; it is idempotent on repeated starts. Back up the DB before migration; new installs initialize the latest schema.
