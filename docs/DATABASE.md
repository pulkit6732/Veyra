# Database

SQLite schema in `veyra.py:SCHEMA`, created via `init()` on startup. Tables: `resolutions` (one explicit adjustment per evidence, note, actor, timestamp, movement reference); `users`, expiring `sessions`; `categories`, `products`, `warehouses`, `locations`; `stock` keyed by `(product_id,location_id)` with integer qty and version; `movements` with unique reference and source/destination, resulting versions, actor and timestamp; `count_sessions` with version/qty captured at start and state; `evidence` linked to one session with observed quantity, version, actor, status and submission time; `deliveries` with unique reference, location, qty and state; `decisions` with stage, reason, relevant evidence ID, stock and version snapshots, actor and timestamp. All quantities are integer units (no fractional UOM conversion). A receive or adjustment bumps its one stock row; transfer bumps each affected row; delivery bumps the source row. Investigation derives expected quantity from the linked count session and compares its captured version to current stock; it selects relevant movements touching that SKU/location with versions after the previous verified count (or the selected count) up to the current version, returning at most 50 with an exact event total. A resolution is inserted atomically with its adjustment movement under `BEGIN IMMEDIATE`, only for the latest still-current discrepant evidence; the version bump makes that evidence stale and forces a recount. Initial seed sets 768 units at version 0 without creating a synthetic receipt and is for a new demo database only. References are globally unique across movements and delivery orders, and a DONE order shares its reference with its own delivery movement. There are no forward migration tools yet: back up the DB before changing schema; new installs initialize the latest schema.
