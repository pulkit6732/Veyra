# Architecture

`index.html` (responsive browser UI) → `veyra.py` (stdlib threaded HTTP + application functions) → SQLite file. No ORM or external package. Each modifying HTTP operation enters `BEGIN IMMEDIATE`: SQLite serializes writers across threads/processes; the delivery commit reads version, stock and evidence and writes the decision, decrement and unique movement within the same transaction. A preflight decision is never trusted at commit. A failed transaction rolls back all its changes. The database enforces unique references, nonnegative stock and quantity checks. Server binds to localhost by default.

Evidence count session snapshots `(SKU, location, version, recorded qty, actor, start time)` before physical counting. Submission is append-only evidence with observed qty and captured version, plus status STALE, VERIFIED or DISCREPANCY. `evidence.status` is a snapshot of submission conditions, not proof of future freshness: delivery always compares captured version to current version. If multiple counts at current version disagree, the order is held; an explicit stock adjustment increments the version, after which workers can recount. Investigation reads the count snapshot, current version, last earlier verified count, relevant bin/version movements and any resolution from persisted tables; event types are evidence, never causal proof. The operator can record a note and explicitly reconcile the latest current discrepant count to its observed quantity; this inserts a movement and resolution atomically and bumps the version, so recount is still mandatory. No automated discrepancy adjustment or causal inference. Deliveries are documents with one or more relational delivery_lines (unique product/bin per document). Legacy header SKU/bin/quantities mirror the first line for compatibility. An existing single-line order is migrated into one line without inventing history. Persisted states: DRAFT → READY → PICKING → PICKED → PACKING → PACKED → DONE. Every step and incremental quantity update is recorded in `delivery_events` with actor, time, scope, pre-transition inventory version and (for DONE) the evidence ID used. PICK and PACK are operational confirmations only: no reservation or stock mutation. Picking is bounded by requested quantity and stock observed at the time; packing is bounded by picked quantity. Inventory may change afterwards; this is why final commit checks again. The official requirements require pick, pack and validation but do not prescribe exact state names. Evidence is required **at final commit**, not at pick/pack: packing may proceed with stale evidence, but final delivery cannot. Both allowed and blocked preflight/commit attempts persist to `decisions`; successful delivery persists one linked `movements` row per line; all line stock changes, movements, DONE events and state transition are in one transaction. Blocked commits leave the order PACKED for recount/retry. A repeated completed order with matching payload or ref-only returns ALREADY_COMPLETED (no second movement); a conflicting ref is rejected. On startup a legacy PENDING/CANCELED order becomes DRAFT and a legacy DONE order stays DONE; no historical pick/pack events are fabricated. Back up before migration. Delivery state and stock changes share the same serialized transaction. Audit timestamps are SQLite UTC seconds; ordering uses event IDs when timestamps coincide.

Limits: receipts and transfers are single-SKU operations; no role-specific permissions, OTP, server push, background job or production TLS. `BEGIN IMMEDIATE` trades concurrent write throughput for simple correct local serialization. SQLite doesn't offer row-level locks; multi-process writers are serialized on the database write lock. Human counts cannot establish actual physical truth without trusted measurement. Count conflict policy is conservative, no supervisor override currently.
